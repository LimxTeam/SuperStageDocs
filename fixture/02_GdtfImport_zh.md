# GDTF 导入

> 适用版本：SuperStage 26H2.6 起 ｜ 前置阅读：[灯具系统总览](00_FixtureSystem_Overview_zh.md)

GDTF（General Device Type Format）是厂商发布灯具数据的标准格式。一个 `.gdtf` 包导进来就是一支可用的灯：通道与模式、几何树与机械轴、3D 模型、图案轮 / 色轮 / 棱镜、缩略图。

---

## 1. 导入会生成什么

一个包按型号生成一组资产：

所有资产都放进 `<输出目录>/<型号>/` 这一个文件夹：

| 资产 | 命名 | 数量 |
| --- | --- | --- |
| 灯具定义 | `<型号>`，**不带前缀** | 1 |
| 通道库 | `CL_<型号>_<模式名>` | 每个 DMX 模式一份 |
| 棱镜预设 | `SP_<型号>_Prism` | 有棱镜时 1 份 |
| 缩略图 | `LTC_<型号>` | 包里带缩略图时 1 份 |
| 图案轮图集 | `LTA_...` | 每个图案轮一份 |
| 色盘图集 | `CLA_...` | 每个色盘一份 |
| 静态网格 | `SM_...` | 包内每个模型一份 |

`<型号>` 的取法：批量导入选 **Brand and Model** 时是 `<厂商>_<型号>`，但如果型号里已经带了厂商名（`ACME SANA PROFILE`）就不重复拼。资产名会做规范化：收掉非 ASCII 字符、连续下划线与首尾下划线。

> 同一批里两个包推出同一个名字时，导入器会**标出撞名但不自动改名**——改成什么得人来定。不处理的话后一个会覆盖前一个，表现是「导了 12 支只出来 11 支」。

## 2. 单个导入

在灯具定义资产上导入，或从内容浏览器新建定义后导入。导入前先设置**导入范围**。

### 2.1 导入范围（九项）

九项按四组划分，关掉哪项，定义里那块数据就原样保留。

| 组 | 选项 | 覆盖的内容 |
| --- | --- | --- |
| 身份 | Identity | 厂商名、型号名 |
| 通道 | Channels | DMX 模式、每个模式的通道库资产、通道→能力绑定 |
| 几何 | Meshes | 网格资产、底座 / 吊挂件、轴层级与枢轴偏移 |
| 几何 | Emitter Placement | 发射器挂在哪一级轴、局部偏移、镜片模型与半径 |
| 几何 | Physical | 灯体外廓尺寸、光通量 |
| 光学 | Gobo Atlases | 图案轮图集 |
| 光学 | Color Atlases | 色盘图集 |
| 光学 | Slot Colors | 把包内槽位的滤片颜色写回通道库 |
| 光学 | Prisms | 棱镜预设，以及回填到槽位的棱镜层选择 |

要点：

- **通道这一项不能再拆**。模式、通道库、绑定三者是在解析模式的同一趟里一起产出的，拆开会得到一份指向旧通道表的绑定，比不导更糟。
- **Channels 是其余几项的落点**。滤片颜色要写回槽位、棱镜层选择要回填槽位。关掉 Channels 时这些会落到既有通道表上——前提是它与本次 GDTF 确实是同一支灯。
- **ZoomRange 一律不动**，导入报告里会说明。
- 自己改过厂商 / 型号名的，重导时关掉 Identity；用美术手工模型的，关掉 Meshes；用手工拼的图案图的，关掉 Gobo Atlases。

### 2.2 绑定是自动推导出来的

GDTF 的属性名是标准化的（`Pan` / `Tilt` / `Dimmer` / `Shutter1` / `ColorSub_C` / `Gobo1` / `Gobo1Pos` / `Prism1` / `Zoom` / `Focus1`…），导入器据此映射到能力操作码，并顺带填好轮序号、分量颜色这些参数——"Gobo1 就是图案轮一号"机器完全推得出来，不该让人再手连二十条。

**映射不中的通道会如实报告为"未识别"，不会被悄悄丢掉**——悄悄丢掉会让人以为导进来就是完整的。

> **没有 GDTF 也能推绑定。** 灯具编辑器的 **Compile** 按钮会先按当前通道库把全部模式的绑定重建一遍再编译。手写通道库、从 MA2 导入、在编辑器里改过属性表，都走这条路——否则手写的灯库永远是空绑定，灯什么都不动。

### 2.3 导入报告

每次导入结束弹出报告，列出解析与导入两个阶段的全部错误、警告与提示。除了模式数、绑定数、图集数、棱镜层数、网格数这些计数，还会按整支灯汇总这几类问题：

| 报告项 | 含义 |
| --- | --- |
| **未识别的属性** | 属性名没有对应的能力操作码，需要手工补绑定 |
| **只有粗调通道的位置属性** | Pan / Tilt 只有 8 位，扫动会有台阶 |
| **轮位已满** | 轮序号只有 1~3 个位置，多出来的属性无处安放 |
| **两条绑定抢同一个轮位** | 轮序号冲突 |
| **发光体色相与属性对不上** | 厂商把通道链到了色相不符的发光体，已保留写死的基色 |
| **色温通道写的是归一化修正量** | 不是开尔文值，端点已按灯具原生白点锚定——否则不修正时会被算成 2700K，明显偏橙 |

以及这类具体提示：

- 某个像素组在包里没有排布位置，全部实例会挤在原点，需要手工设置发射器的 Span X/Y；
- 某个组在包里声明为 `BeamType=Glow/None`，按不投射光柱的辉光发射器创建（光环 / 背板一类）；
- 包内只有 `PrimitiveType` 占位、没有实际模型文件，按占位灯体生成。

## 3. 批量导入

**打开方式**：SuperStage 工具栏 → **SuperDMXTool** → **GDTF Batch Import**

### 3.1 流程

1. **Add GDTF...** 或 **Browse...** 选一批 `.gdtf` 包，列表显示序号、文件、厂商、型号与状态；
2. 设置 **Output folder**——新灯要落进的灯库目录。目录原样使用，每支灯在里面各占一个子文件夹，所以往已有的厂商文件夹里补几支灯是可以直接用的；
3. 选择命名方式：**Brand_Model** 或 **Model only**；
4. 按 **Create fixtures**。运行中显示进度，结束给出汇总。

**Clear** 只清空列表，不动已经建好的资产。单条右键可从列表移除。

### 3.2 三个开关

| 开关 | 说明 |
| --- | --- |
| **Compile after import** | 导入后立即编译成运行时产物并存进资产。不开的话每次载入都要重编一遍。没有特别理由就开着 |
| **Copy GDTF into library** | 先把每个包复制进 `FixtureLibrary/GDTF/<厂商>/` 再从那里导入。**从下载文件夹导入时务必开着** |
| **Save each fixture** | 每建好一支就落盘。一支灯是很多个文件，几百支不落盘会把编辑器拖垮 |

> **Copy GDTF into library 为什么重要**：导入器会记住源 GDTF 在哪。直接从下载目录导，记的就是那个目录；等目录被清掉，"从源 GDTF 原地升级"再也找不到源文件，MVR 导出也会把这支灯报成缺少 GDTF 包。文件名不会被改动。

### 3.3 状态列

列表最后一列是状态。运行**之前**它只报一种问题：

| 状态 | 含义 | 怎么办 |
| --- | --- | --- |
| **duplicate target** | 列表里有两个包会生成同名资产，后建的会覆盖先建的 | 改用 **Brand_Model** 命名，或分两次导进不同目录 |

运行**之后**逐包报结果：

| 状态 | 含义 |
| --- | --- |
| **Created** | 新建成功 |
| **Updated** | 同名灯具已存在，已刷新 |
| **compile errors** | 灯建出来了，但包里有内容没能干净地转换过来。可能仍然可用，正式用之前先检查 |
| **Package failed** / **Import failed** | 包读不出来。多半是下载损坏，重新下一份 |
| **Bad target path** | 输出目录不是合法的灯库路径 |
| **save failed** | 灯建出来了但写不进磁盘。检查目录是不是只读 |

### 3.4 导入之后

新灯会出现在资产浏览器里，可以直接拖进场景，放好之后配接。

包里的内容不一定都能自动转换过来，可能有个别通道没被识别。哪里行为不对，就在灯具编辑器里打开这支灯，去 Validation 页看通道。

## 4. 原地升级

灯具定义右键 → **Upgrade from source GDTF**。

**用途**：灯库已经建了几百支之后，导入器又长出了新能力（发射器安装朝向、ModeMaster 条件通道、占位灯体）。这些对已经做好的灯全部缺席，而重导入要么够不着（排布挂在通道那一趟里），要么代价太大（ModeMaster 要连通道表一起重建，手调过的绑定全部作废）。

**它只做加法**：源文件里有、资产里没有的补上，既有的通道表、绑定、轮盘与手工模型一律不碰。**这不是重导入。**

### 4.1 三个选项与它们的风险

**手调过的东西没有任何标记，代码分不出"这个偏移是导入器写的"还是"这个偏移是人摆的"**——所以凡是会覆盖既有值的项一律默认关闭。

| 选项 | 默认 | 风险 |
| --- | --- | --- |
| **ModeMaster conditional channels** | **开** | **安全。**只写子属性上那 4 个新字段，通道表其余一个字节不动。这 4 个字段是后加的，既有资产里必然全空，手工也补不出来（条件写在 GDTF 的 ChannelFunction 上），所以不存在覆盖手工成果的可能 |
| **Emitter placement** | 关 | **会覆盖手摆的发射器。**整块重写 Layout / Count X / Count Y / Span X / Span Y / Local Offset / Local Rotation / 逐实例变换——恰好就是手工摆矩阵灯时会动的那批字段。按发射器名对号，只更新已有的，**绝不新建发射器** |
| **Generate a body for fixtures that have none** | 关 | **会覆盖枢轴。**只对"一个灯体网格都没有"的定义生效。网格本身是纯补空，但**枢轴偏移是连着一起写的**——网格原点必须落在枢轴上，只给网格不给枢轴就是装歪。而没有灯体的灯恰恰最可能被手工摆过枢轴 |
| **Report only — change nothing** | **开** | 全套匹配照跑，一个字节都不写、也不弄脏任何资产，只报"会改多少" |

**第一次就让 Report only 开着。** 数字回来是 0 就根本不用纠结；已经上线的灯库更该先零风险地问一句"要不要动它"。勾着它时按钮显示 **Check**，取消后才显示 **Upgrade**。

后两项建议**逐支灯确认后再开**——重做一遍手工活的代价远大于少补一项数据。

### 4.2 它怎么找到源 GDTF

源文件路径记在**通道库**资产上（每个模式一份），不在定义上，取第一个非空的。

导入时写进去的是绝对路径，换机器或整理过灯库目录就会失效——对不上时会**按文件名在灯库根目录下递归再找一遍**（灯库文件名一律沿用下载原名，同名即同一个包）。两条路都找不到时这支灯会被跳过并在报告里点名。

### 4.3 报告与保存

报告给出：会改 / 已改的灯具数、重算排布的发射器数、补上的 ModeMaster 条件数、生成的占位灯体数、以及"已经什么都不缺"的数量；另外单独列出**没有记录源 GDTF 或文件已丢失**的灯，和**解析失败**的灯。

**改过的资产被标脏但不会自动保存**——自己审一遍再存。

## 5. 当前实现覆盖到什么程度

| 内容 | 状态 |
| --- | --- |
| DMX 模式与通道 | 导入 |
| 通道功能与通道集合（槽位） | 导入 |
| ModeMaster 条件通道 | 支持，区间按条件分组 |
| 几何树与机械轴 | 导入，含轴的行程声明 |
| 3D 模型 | 导入，`.3ds` 与 `.glb` 兜底，按包内 `<Model>` 声明尺寸归一化 |
| 图案轮 / 色盘 | 生成图集 |
| 棱镜 | 生成棱镜预设资产 |
| 缩略图 | 导入为灯具图标 |
| 物理参数 | 导入灯体尺寸与光通量 |

其它说明：

- 包内 zip 条目名按 UTF-8 解码，中文命名的模型不会丢失；
- 个别高压缩率打包的 GDTF 依赖系统解压工具完成读取（仅 Windows）；
- 灯库数据的准确性以厂商发布的包为准。同一支灯不同厂商版本的写法差异很大，导入后请在灯具编辑器里核对。

## 6. 导入后必须确认的三件事

### 6.1 光束类型

**新导入的灯，主发射器默认是 Material Beam（Legacy）**；带刀片通道的成像灯默认是 Shaper（Legacy）。要用体积光束需要在灯具编辑器的发射器里手动改成 `Volumetric Beam` 或 `Volumetric Shaper (Profile)`。

矩阵 / 像素组不受这条影响：它们按包内 BeamType 判定为 Ray Beam，声明为不投射光柱的（光环、背板）判定为 Wash。

### 6.2 未绑定的通道

看灯具编辑器的 **Validation** 页。控制类通道（Reset、Lamp On）没有画面表现是正常的；一条明显该有表现的通道出现在未绑定列表里，说明属性名与绑定规则对不上，需要手工补一条绑定。

### 6.3 逐通道试灯

用灯具编辑器的 **DMX Test** 页把每条通道推一遍，确认 Pan/Tilt 行程、颜色、图案、棱镜、切割的实际表现。

---

## 7. GDTF 导出

灯具编辑器与通道库编辑器都可以导出 GDTF。导出按 GDTF 1.2 结构组织，会补回模式与函数名，往返不丢数据。

导出内容以 DMX 数据为主；`Wheels` 与 `PhysicalDescriptions` 子节点为空占位，不含轮盘图片或物理描述数据。兼容性需在目标软件中验证。
