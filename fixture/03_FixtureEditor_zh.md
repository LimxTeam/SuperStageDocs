# 灯具编辑器

> 适用版本：SuperStage 26H2.6 起 ｜ 前置阅读：[灯具定义资产](01_FixtureDefinition_zh.md)

灯具编辑器用于编辑一份灯具定义：它的 DMX 模式、活动部件、光束与轮盘。

**打开方式**：内容浏览器双击灯具定义资产（型号文件夹里那个与文件夹同名、不带前缀的资产），或在场景中右键一支灯选择编辑其定义。

面板右上角有帮助按钮，内容与本文一致。

---

## 1. 界面布局

窗口分左右两栏。

**左侧约三分之二是实时预览**——真实的灯具带着真实的光束，驱动方式与它在场上时相同。视口带 UE 自带的视口工具栏，可以环绕、切正交相机、切线框看灯体。

**右侧四个页签，两两一组**：

| 位置 | 页签 | 内容 |
| --- | --- | --- |
| 上半（默认显示 Fixture） | **Fixture** | 定义本身。分组：身份、物理数据、活动部件、出光位置、轮盘与棱镜、DMX 模式 |
| | **DMX Test** | 手动推通道，看预览的反应 |
| 下半（默认显示 Channel Map） | **Channel Map** | 一眼看完整个地址占位 |
| | **Validation** | 当前这支灯有哪些问题 |

这样分组是有道理的：Fixture 与 DMX Test 是"**改一条 → 推一下看效果**"的来回，同组切换比并排省地方也不用左右扫视；Channel Map 与 Validation 看的是同一件事——校验说的就是"哪条通道绑错了"，切一下就能对上。

> Test、Channel Map 与 Validation 三页读的都是**编译产物**，所以在第一次按 Compile 之前它们是空的。

### 1.1 顶部工具栏与概览条

工具栏四个按钮：**Compile**、**Import GDTF**、**Import JSON**、**Export JSON**。

右边是规模概览，随定义实时更新：

```text
Modes 2  ·  Emitter instances 25  ·  Ops 41  ·  Channels 39
```

| 项 | 含义 |
| --- | --- |
| **Modes** | DMX 模式数 |
| **Emitter instances** | 全部发射器按排布展开后的运行时组件总数。**这是这支灯的规模指标**——一个 Count X = 25 的圆周排布在这里就是 25 |
| **Ops** | 默认模式编译出的操作码条数 |
| **Channels** | 默认模式的通道跨度 |

后两项取的是**默认模式的编译产物**，没编译过时显示 0。

## 2. 从厂商包起步

很少有人从零建一支灯。**Import GDTF** 读厂商自己的包把定义填好——通道、轮盘、模型都在里面。

导入对话框可以选**导入哪几部分**。这在重导时很关键：**没勾的部分原样保留**。所以如果你手工调过活动部件、而厂商刚发布了新的图案图，只勾图案图集，你的调整就能保住。

> **勾上的部分是整块替换，不是合并。** 不想被冲掉的一律取消勾选。

一整个文件夹的包要一次导，用批量导入工具，别在这里一个一个来。详见 [GDTF 导入](02_GdtfImport_zh.md)。

---

## 3. 编译与 Validation 页

**Compile** 按顺序做两件事：

1. **按当前通道库把全部模式的绑定重建一遍**；
2. 编译成运行时产物，并跑一遍校验。

两步合成一个按钮是有意的：绑定是从通道库的属性表按规则推出来的，改了库不重建就等于拿旧绑定去编译，产物与库对不上；重建完不编译，产物又还是旧的。两件事从来都要一起做。它们**在同一个事务里**，撤销一次会把两者一起退回，不会留下"绑定已换、产物还是老的"这种半截状态。

**任何改动之后都要按一次**——不按，改动不会反映到场上。

> **这也是手写通道库唯一的出绑定途径**：绑定原先只有 GDTF 导入才会产出，手写的库如果不按这个按钮就永远是空绑定、灯什么都不动。

编译失败时会弹窗提示去 Validation 页看具体错误。

### 3.1 Validation 页怎么读

结果按严重程度排序，每行的格式是：

```text
✕  Standard 39CH / binding 7    Attribute 'Zomm' not found in the channel library.
⚠  Standard 39CH                Channel 'Iris' is defined in the library but not bound to any capability.
```

| 级别 | 含义 |
| --- | --- |
| ✕ Error | 这支灯不能用，必须修。**任何一条 Error 都会让编译产物作废** |
| ⚠ Warning | 能用，但多半不是你想要的结果 |
| ℹ Note | 值得知道，不用处理 |

行首符号后面是**位置前缀**：模式名，以及能定位到具体绑定时附带 `/ binding N`——照这个序号回 Fixture 页的绑定表数即可。没有问题时摘要显示 `Validation: no issues.`

全部诊断的逐条成因见[灯具构建器](06_FixtureBuilder_zh.md)第 6 节。

### 3.2 与内容浏览器右键 Compile 的区别

内容浏览器右键灯具定义也有 **Compile**，支持多选批量，但**它只编译，不重建绑定**。改过通道库之后要用**编辑器里的**这个按钮；右键批量编译是给"改过导入器或编译器之后把整个灯库刷一遍"用的。

两个入口编译完都只把资产**标脏，不会自动保存**。不保存的话每次加载都要重编一遍。

## 4. DMX Test 页

每条通道一个滑块，值直接送进预览——这是确认"Pan 是不是真的在摇、出来的图案是不是你要的那个"最快的办法。

| 按钮 | 作用 |
| --- | --- |
| **Default** | 打开调光与快门，把 Pan / Tilt / Zoom 归中，一键让灯做点正常的事 |
| **Blackout** | 全部归零 |

带命名槽位的通道（图案轮、色盘）会多一个 **slots** 按钮，按名字挑槽位，不用去猜原始值。

旁边还有两个查看辅助：

| 辅助 | 作用 |
| --- | --- |
| **Rig** | 在模型上画出每根轴的旋转线、枢轴与行程弧。这是确认枢轴到底有没有落在机械关节上的唯一可靠办法 |
| **Floor** | 光斑挡住灯体时把地板藏起来 |

---

## 5. Channel Map 页

把当前模式的地址占位铺成一张格子图，一格一个通道，并用一行字说明其中有多少真正在用。悬停一格能看到是谁占的。

它存在的意义是抓通道表最常犯的三个错：

| 问题 | 表现 |
| --- | --- |
| **冲突** | 两个属性占同一条通道。只有一个会被听见 |
| **空洞** | 模式声明了、却没有任何绑定指向的通道。通常是导入失败的通道，或者你本来打算填的 |
| **越界** | 绑定伸到了声明跨度之外。这支灯在悄悄读下一支灯的通道 |

---

## 6. 共享一支灯

| 按钮 | 作用 |
| --- | --- |
| **Export JSON** | 把整支灯写成一个文件，可以发给别人，也可以在做危险改动前留个备份 |
| **Import JSON** | 读回来。**它替换整支灯**，不是替换其中一部分——这里有想留的东西请先导出 |

## 7. 排查

### 预览里没有光束

第一次打开或改完之后，先按 **Compile**。预览读的是编译产物。

### 灯在场上不亮

1. 定义编译过了吗；
2. 发射器的光束类型是什么——`Spot Only` 与 `Wash` 本来就不画空中光柱；
3. 场景里灯具的 DMX 模式与 Universe / 起始地址对不对（见 [DMX 灯具基础](../stagecore/03_DMX_Actor_Base_zh.md)）。

### 控台推得动，画面没反应

去 Validation 页看这条属性在不在未绑定列表里。控制类通道（Reset、Lamp On）没有画面表现是正常的。

### Pan / Tilt 行程不对

看 Fixture 页对应轴的 **Range**。它应当是从 GDTF 包内声明导入的值。用 DMX Test 页的 **Rig** 辅助确认枢轴位置。

### 图案或颜色整轮对不上

看光学分组里那个轮的**格数**是否与图集实际格数一致。格数错了，材质会按错误的格宽去切图集，整轮都会错位。
